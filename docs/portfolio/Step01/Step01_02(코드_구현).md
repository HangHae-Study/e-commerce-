# TDD로 코드 완성 해보기.

## 유저 포인트 조회를 위한 기본설계
0. 테이블 클래스는 수정하지 않기 때문에, 인프라 레벨에서 제공하는 틀(요구사항)이 이미 정해져 있다고 가정.
   1. 유저를 조회 시, 없는 유저라면 0포인트를 가진 신규 유저가 리턴 됨.
```java
@Component
public class UserPointTable {

    private final Map<Long, UserPoint> table = new HashMap<>();

    public UserPoint selectById(Long id) {
        throttle(200);
        return table.getOrDefault(id, UserPoint.empty(id));
    }
}
```

1. RED: 유저를 조회한다.존재하지 않는 유저라면 새로운 ID와 0포인트를 가진 유저가 반환된다.
2. GREEN: 서비스 코드에서 유저를 리턴하는 통과성 코드를 작성
3. BLUE(Refactoring)
   - id 기반 조회 검증
   - Refactoring: 테이블 요구사항이 깨지지 않도록, 추상화를 통해 테스트 결합도 낮추기

### 3) BLUE & Refactoring
- 테이블 정책에 따라서, 더 이상 코드를 수정하거나 도메인 정책을 추가할 필요는 없다.
- 단순 조회라는 기능이고, `없는 유저에 대해서 0포인트를 가진 신규 유저를 리턴한다`는 기준이 변경되지 않는다면, 해당 테스트 코드는 더 작성할 필요가 없는 것 처럼 느껴진다.


- 다만, 인 메모리 클래스를 활용한 테이블 정보라는 것을 감안하여, 클래스간 결합도를 만드는 테스트 코드는<br/> 추후 비즈니스 로직 수정에 따라서 제약사항이 생길 수 있으므로, 추상화를 통해 결합도를 낮추고 응집도를 올려볼 수 높일 수 있을 것 같다.

### `현재 코드는, 특정 테이블 클래스에 종속적인 테스트`
- 이를 분리하기 위해, 정보를 `CRUD`하는 공통 기능을 추상화하고, 이를 기반으로 Stub 또는 Mock기법의 테스트 코드를 작성한다.

서비스 클래스는 Stub을 통해서 조회된 유저에 대한 결과만을 바라볼 수 있다.

## 유저 포인트 충전을 위한 설계
0. 테이블 클래스는 수정하지 않기 때문에, 인프라 레벨에서 제공하는 틀(요구사항)이 이미 정해져 있다고 가정.
   1. 기존 맵 필드에 새로운 객체를 덮어 씌움.
   ```java
    public UserPoint insertOrUpdate(long id, long amount) {
        throttle(300);
        UserPoint userPoint = new UserPoint(id, amount, System.currentTimeMillis());
        table.put(id, userPoint);
        return userPoint;
    }
    ```

1. RED: 
   - 유저를 조회한다. (이미 완성)
   - 기존 유저의 포인트에 충전 값을 더한다.
2. GREEN : 
   - 서비스 코드에서 증가된 유저를 리턴하는 통과성 코드 작성
3. BLUE(Refactoring) : 
   - 유저 충전의 책임을 어디에 둘지 정한다.
   - 유저 충전 시 정책을 검증할 수 있도록 한다. 

### 1) RED
```java
@Test
public void TEST_02_유저_포인트를_충전한다(){
    // given
    long id = 1L;
    long amount = 100L;
    UserPoint before = new UserPoint(id, 50L, 0L);
    UserPoint after  = new UserPoint(id, 150L, System.currentTimeMillis());

    given(userPointTable.selectById(id)).willReturn(before);
    given(userPointTable.insertOrUpdate(id, 150L)).willReturn(after);

    // when
    UserPoint result = pointService.chargeUserPoint(id, amount);

    // then
    assertThat(result.point()).isEqualTo(150L);
    assertThat(result.id()).isEqualTo(id);

    // 상호작용 검증
    verify(userPointTable).selectById(id);
    verify(userPointTable).insertOrUpdate(id, 150L);
}
```
### 2) GREEN
### `더하는 행위를 하여 리턴하는 통과성 코드 작성`

```java
@Service
@RequiredArgsConstructor
public class PointService2 {
    private final UserPointRepository userPointTable;
    private final PointHistoryTable pointHistoryTable;

    public UserPoint getUserPoint(Long id){
        return userPointTable.selectById(id);
    }
    
    public UserPoint chargeUserPoint(Long id, Long point){
        UserPoint current = userPointTable.selectById(id);
        long amount = current.point() + point;
        return userPointTable.insertOrUpdate(id, amount);
    }
}
```

### 3) BLUE & Refactoring
- 현재 유저 충전의 경우, 더하는 행위는 공통의 관심사이다.
- 충전 서비스 뿐만 아니라, 유저의 기존 포인트에 값이 더해지는 행위는 다른 곳에서도 일어날 수 있다.
- 그렇기 때문에, 이에 대한 행위를 도메인 레벨로 내려서 공통의 기능을 하나의 클래스에 책임을 가지도록 하기.
- 또한, `포인트 증가에 대한 정책을 추가할 때마다` 호출 되는 모든 곳에 코드를 수정하는 것보다, 도메인 레벨에서 결합도가 없이 처리하는 것이 깔끔한 코드가 될 것이다.

### 3-1) 도메인 클래스 수정
#### [1] : 더하는 행위를 도메인 에서 제공하기
```java
public record UserPoint(
        long id,
        long point,
        long updateMillis
) {

    public static UserPoint empty(long id) {
        return new UserPoint(id, 0, System.currentTimeMillis());
    }

    public long charge(long point) {
        return this.point() + point;
    }
}
```
#### [2] : 더하는 과정 중에 정책을 추가하기.
```java
public record UserPoint(
        long id,
        long point,
        long updateMillis
) {

    public static UserPoint empty(long id) {
        return new UserPoint(id, 0, System.currentTimeMillis());
    }


    public long charge(long amount){
       if(amount <= 0){
          throw new RuntimeException("Charge Should Be Positive");
       }
      
       if(amount >= 1000000L){
          throw new RuntimeException("Charge Should Be Less Then a Million");
       }
      
       return this.point() + amount;
    }
}
```

### 3-2) 도메인 클래스 단위 테스트
```java

public class PointDomainTest {

    @Test
    public void TEST01_유저_포인트를_정상_충전한다(){
        UserPoint before = UserPoint.empty(1L);

        long amt = 100L;
        long afterPoint = before.charge(amt);

        assertThat(before.point() + amt).isEqualTo(afterPoint);
    }

    @Test
    public void TEST02_유저_포인트를_음수_충전하여_실패한다(){
        UserPoint before = UserPoint.empty(1L);

        long amt = -100L;

        assertThatThrownBy(() -> before.charge(amt))
                .hasMessageContaining("Charge Should Be Positive");
    }

    @Test
    public void TEST03_유저_포인트를_한계치_이상_충전한다(){
        UserPoint before = UserPoint.empty(1L);

        long amt = 1111111L;
        assertThatThrownBy(() -> before.charge(amt))
                .hasMessageContaining("Charge Should Be Less Then a Million");
    }
}
```

#### 3-3) 서비스 코드 수정
```java
@Service
@RequiredArgsConstructor

    private final UserPointRepository userPointTable;
    private final PointHistoryTable pointHistoryTable;

    public UserPoint getUserPoint(Long id){
        return userPointTable.selectById(id);
    }
    
    public UserPoint chargeUserPoint(Long id, Long point){
        UserPoint current = userPointTable.selectById(id);

```

- 도메인 클래스에 충전에 대한 기능과 정책을 모두 할당 해주었으므로, 다른 클래스는 이를 호출만 하여 결합도를 낮출 수 있다.
- (충전에 대한 기능이 변경 되면, 도메인 클래스를 수정하면 되기 때문)


- 또한, `포인트를 더하는 행위`는 도메인 클래스의 단위 테스트를 성공적으로 작성 & 통과 시켰기 때문에, `서비스에 대한 충전 테스트는 추가로 진행하지 않아도 될 것` 같다!

## 테스트 코드에 사용되는 여러 클래스 정리

### 1. JUnit 5 Core — 테스트 라이프사이클

> `org.junit.jupiter.*`

| 키워드 | 용도 | 호출 방식 | 자주 쓰는 포인트 |
|--------|------|-----------|----------------|
| `@Test` | 테스트 메서드 표시 | 메서드 위에 선언 | 단위 테스트 기본, given-when-then 구조와 함께 사용 |
| `@BeforeEach` | 각 테스트 실행 전 초기화 | 메서드 위에 선언 | 공통 데이터 준비, mock 초기화 |
| `@ExtendWith(MockitoExtension.class)` | Mockito 활성화(JUnit5) | 클래스 위에 선언 | `@Mock`, `@InjectMocks` 자동 동작 |

### 2. JUnit 5 Parameterized — 파라미터 반복 테스트

> `org.junit.jupiter.params.*`

| 키워드 | 용도 | 호출 방식 | 자주 쓰는 포인트 |
|--------|------|-----------|----------------|
| `@ParameterizedTest` | 여러 파라미터로 테스트 반복 | 메서드 위 선언 | 경계값/여러 케이스 테스트에 적합 |
| `@MethodSource` | 파라미터 공급자 | `@MethodSource(“method”)` | 복잡한 Arguments 제공용 |
| `Arguments` | 파라미터 세트 | `Arguments.of(a, b)` | 파라미터 묶음 생성 |
| `Stream` | MethodSource 반환 스트림 | `Stream.of(...)` | 여러 테스트 case 생성 (`java.util.stream.Stream`) |

### 3. Mockito — Mock/Stub/Verify

> `org.mockito.*`

| 키워드 | 용도 | 호출 방식 | 자주 쓰는 포인트 |
|--------|------|-----------|----------------|
| `@Mock` | Mock 객체 생성 | 필드 위 선언 | 외부 의존성(mocking) 분리 |
| `@InjectMocks` | Mock 주입된 테스트 대상(SUT) 생성 | 필드 위 선언 | 서비스 테스트에서 Mock 자동 주입 |
| `given()` | Mockito BDD 스타일 stubbing | `given(mock.method()).willReturn(...)` | 조건/상황 가정(given) 작성 |
| `verify()` | Mock의 호출 여부 검증 | `verify(mock).method()` | times(), never() 등과 콜라보 |
| `times()` | 호출 횟수 검증 | `verify(mock, times(1))` | 정해진 횟수 검증 |
| `anyLong()` | 인자 매칭(any long) | `anyLong()` | 인자 자유롭게 테스트 |
| `eq()` | 특정 값과 동일 매칭 | `eq(1L)` | 특정 파라미터를 강제하고 싶을 때 |

### 4. AssertJ — 검증 (Assertion)

> `org.assertj.core.api.Assertions.*`

| 키워드 | 용도 | 호출 방식 | 자주 쓰는 포인트 |
|--------|------|-----------|----------------|
| `assertThat()` | 검증 메서드 | `assertThat(value).isEqualTo(...)` | 체이닝 형태로 가독성 좋은 검증 |
| `assertThatThrownBy()` | 예외 발생 검증 | `assertThatThrownBy(() -> ...)` | 실패/경계/에러 테스트 때 필수 |

### 5. Spring Test — 통합 테스트 및 Controller 테스트

> `org.springframework.boot.test.*`, `org.springframework.test.web.servlet.*`

| 키워드 | 용도 | 호출 방식 | 자주 쓰는 포인트 |
|--------|------|-----------|----------------|
| `@SpringBootTest` | 스프링 전체 Context 로딩 | 클래스 위 선언 | 통합 테스트, 실제 빈 기반 테스트 |
| `@AutoConfigureMockMvc` | MockMvc 자동 구성 | 클래스 위 선언 | Controller 테스트 시 MockMvc 사용 |
| `@Autowired` | 스프링 빈 주입 | 필드 위 선언 | MockMvc, Repository, Service 등 inject |
| `MockMvc` | Controller를 HTTP처럼 테스트 | `mockMvc.perform(...)` | API 테스트 핵심, JSON/Status 검증 |
| `MvcResult` | MockMvc 응답 결과 객체 | `.andReturn()` | 응답 body 파싱, 다음 요청에 활용 |
| `status()` | HTTP status 검증 | `.andExpect(status().isOk())` | 응답 코드 필수 검증 |
| `jsonPath()` | JSON 응답 필드 검증 | `.andExpect(jsonPath(“$.data.point”).value(...))` | 응답 구조 계약 테스트 |
| `get()` | MockMvc GET 요청 빌더 | `mockMvc.perform(get(“/url”))` | REST 컨트롤러 GET 테스트 |
| `patch()` | MockMvc PATCH 요청 빌더 | `mockMvc.perform(patch(“/url”))` | 부분 업데이트, 충전 등 이벤트성 API 테스트 |
| `MediaType` | 요청/응답 ContentType 정의 | `.contentType(MediaType.APPLICATION_JSON)` | JSON body 전송 필수 |

### 사용 예시

```java

    }
```

