# STEP 01 (TDD - 기능 추가 및 테스트 구현)

## `STEP01 - 기능 추가 및 테스트 구현`

Summary : 유저/포인트 도메인을 기반으로 TDD 기반의 설계와 비즈니스 로직 완성하기.

- 포인트 충전, 사용에 대한 정책 추가 (잔고 부족, 최대 잔고 등)
- 4가지 기본 기능 (포인트 조회, 포인트 충전/사용 내역 조회, 충전, 사용)에 대한 구현
- 4가지 기본 기능에 대한 테스트 작성
- 단, 이때 `/database` 패키지의 구현체는 수정하지 않고, 이를 활용해 기능을 구현함

> 유저, 포인트라는 도메인을 기반으로 데이터베이스에 종속적이지 않은 `포인트 충전/사용/조회` 기능에 대한 기본 코드와 테스트 코드를 작성하기.

## 학습 목표
- 테스트 코드에 대한 개념과 필요성을 확립
- TDD 개발론의 방식과 장점을 활용하여 코드 설계 및 명세화 견고하게
- `Red - Blue - Green` 단계를 통한 검증.
- 테스트 코드를 기반으로한 견고한 설계로, 변화에는 폐쇄적이고 확장에는 개방적인 코드를 지향하기.

## 내가 생각하는 TDD의 목적
- 처음 설계를 통해서 개발이 완료된 로직이 있다고 한다면, 클래스 간의 결합은 어느정도 발생할 수 있다는 가정을 한다.
- 하지만, 추후에 설계에 대한 변경이나, 요구사항 추가로 인해 우리의 비즈니스 로직을 수정해야한다면?
  - 기존 비즈니스 로직의 변경으로 인해 결합되어 있던 클래스간의 로직이나 코드에 수정이 발생하여, 테스트 코드가 깨질 수 있음.


- 테스트 기반의 코드를 우선 작성하고, `Red - Blue - Green` 단계의 테스트 및 비즈니스 코드 작성은, 추후 설계에 대한 코드 명세서가 될 수 있다.
- 사전에 정의된 명세로 인해, 코드 수정 시 어느 부분이 깨질 지를 미리 파악하고, 변경이 가능하다.


- 이에서 더 확장하여, `각 계층별 테스트(단위/통합)를 추상화하여 상호 클래스간의 결합도를 낮추고`, 변화에 폐쇄적이고 확장에 개방적인 비즈니스 로직을 설계하기.

## Template Code

### PointHistory
```java
@Component
public class PointHistoryTable {
    private final List<PointHistory> table = new ArrayList<>();
    private long cursor = 1;

    public PointHistory insert(long userId, long amount, TransactionType type, long updateMillis) {
        throttle(300L);
        PointHistory pointHistory = new PointHistory(cursor++, userId, amount, type, updateMillis);
        table.add(pointHistory);
        return pointHistory;
    }

    public List<PointHistory> selectAllByUserId(long userId) {
        return table.stream().filter(pointHistory -> pointHistory.userId() == userId).toList();
    }

    private void throttle(long millis) {
        try {
            TimeUnit.MILLISECONDS.sleep((long) (Math.random() * millis));
        } catch (InterruptedException ignored) {

        }
    }
}

public record PointHistory(
        long id,
        long userId,
        long amount,
        TransactionType type,
        long updateMillis
) {
}
```

### UserPoint
```java
@Component
public class UserPointTable {

    private final Map<Long, UserPoint> table = new HashMap<>();

    public UserPoint selectById(Long id) {
        throttle(200);
        return table.getOrDefault(id, UserPoint.empty(id));
    }

    public UserPoint insertOrUpdate(long id, long amount) {
        throttle(300);
        UserPoint userPoint = new UserPoint(id, amount, System.currentTimeMillis());
        table.put(id, userPoint);
        return userPoint;
    }

    private void throttle(long millis) {
        try {
            TimeUnit.MILLISECONDS.sleep((long) (Math.random() * millis));
        } catch (InterruptedException ignored) {

        }
    }
}

public record UserPoint(
        long id,
        long point,
        long updateMillis
) {

    public static UserPoint empty(long id) {
        return new UserPoint(id, 0, System.currentTimeMillis());
    }
}
```

### 코드를 보고 느낀 점

- 도메인의 순서 : `User - > Point` (여기서 유저가 충전 행위를 한다면?)
  1. PointHistory에 해당 행위에 대한 데이터를 입력하고, 수행된 최종 결과를 UserPoint의 현재 포인트를 반영하기.


- 해당 구조에서 추후에 확장될 수 있을 만한 부분?
  - 추후, 포인트 사용/충전 기록 조회 시 PointHistoryTable 이 사용될 수 있음.
  - 환불 시에 PointHistoryTable 기반으로, 포인트 사용/감소 여부 판별
    - 이미 포인트를 사용했으면, 환불이 불가능함.
  - (동시성 문제는 기능 구성 먼저 완료 후 생각)


- 충전 방식
  1. 단순 순차적 방식
     - 현재 UserPoint 를 최신화하고, (현재 UserPoint `+ or -` newPoint )
     - 충전/사용 내역을 PointHistory 에 추가한다.
  2. 검증 후 변경 방식
     - PointHistory 에서 집계 된 결과에서 마지막 Point를 현재 유저 Point와 비교한다.
     - 그 다음, UserPoint의 point 칼럼에 최신화를 한다?


- 고려 해야할 점
  - 각 테이블 마다 throttle이 존재하는 것을 보았을 때, 서비스에서 저장 요청을 보냈을 때 공유 자원에 대한 접근 또한 신경을 써야할 것 같다.
  - `i. 순차적방식`을 썻을 때, 동시성 접근 시에는 충전/사용 순서가 꼬일 수 있음.
  - `ii. 검증방식`을 썻을 때, 매 충전/감소 마다 공유자원을 선점하면서, 동시성 접근을 방지하지만 부하가 발생할 수 있음.

## 기능 설계

- 요구 사항 정의
  - `PATCH /point/{id}/charge` : 포인트를 충전한다.
  - `PATCH /point/{id}/use` : 포인트를 사용한다.
  - `GET /point/{id}/histories` : 포인트 내역을 조회한다.
  - `GET /point/{id} `: 포인트를 조회한다.
- 기능 요구사항
  - 잔고가 부족할 경우, 포인트 사용은 실패하여야 합니다.


- Table 구조 파악하기
  - PointHistory `포인트 충전/사용 내역`
    - ID (히스토리 테이블 식별자)
    - 유저 ID (포인트 충전한 유저 식별자)
    - 충전량 (충전 포인트 금액)
    - 트랜잭션 타입 (충전 : CHARGE, 사용 : USE)
    - 변경 시간 (Milli초)
  - UserPoint `유저가 가진 포인트`
    - ID : 유저 ID
    - 포인트 : 현재 유저가 가지고 있는 포인트 금액
    - 변경 시간 (Milli초)

## TDD(Test Driven Develop) 기반의 코드 작성

### 우선순위
- 현재는 프로젝트 내부에 클래스로 정의된, 인 메모리 객체를 통해서 데이터를 관리한다.
  - 이 구조는 추후에 외부 DB로 변경될 수 있는 가능성이 충분하기 때문에, DB에서 사용될 수 있는 기능을 공통으로 묶어서 추상화 할 필요가 있음.
  - 다만, DB 클래스를 수정할 수 없기 때문에, 해당 클래스를 종속적으로 가지게 되는 서비스 클래스를 추상화하여 테스트 코드를 작성하면 좋을 것.

### Stub vs Mock

| 구분 | Stub (스텁) | Mock (목)                                                              |
|------|-------------|-----------------------------------------------------------------------|
| 주요 목적 | 테스트를 위한 데이터나 응답을 제공하여 테스트 대상이 외부 의존성 없이 동작하게 함. | 테스트 대상이 외부 의존성과 올바르게 상호작용했는지 (예: 특정 메서드가 호출되었는지, 몇 번 호출되었는지) 검증함.     |
| 검증 방식 | 상태 검증 (State Verification): 테스트가 끝난 후 객체의 상태가 예상대로인지 확인. | 행위 검증 (Behavior Verification): 테스트 과정에서 객체가 예상한 행위(메서드 호출 등)를 했는지 확인. |
| 예시 | 데이터베이스에서 특정 데이터를 반환하도록 설정. | 이메일 발송 메서드가 호출되었는지, 슬랙 메시지가 전송되었는지 확인.                                |
| 추가 설명 | Stub을 사용하는 것은 단순히 리턴이나 실제 코드 대신 단순한 값을 반환하는 메커니즘을 삽입하는 것. | Mock은 외부의 의존성을 '모의'하여 테스트의 격리성과 신뢰성을 높이는 데 중점을 둠.                     |

- Stub: "이런 값이 필요해." → 상태를 제공하여 테스트의 실행을 가능하게 합니다.
- Mock: "이 메서드가 이렇게 호출되었어야 해." → 행위를 검증하여 테스트의 정확성을 확인합니다.


### 유저/포인트 도메인에서?
- `유저테이블`, `포인트테이블` 을 호출하는 서비스 코드에서는 각 테이블에 대한 결과가 올바르게 리턴되는지를 확인하기 위해, Stub 형태를 선택하는 것이 더 나은 것처럼 느껴진다.
- 왜냐하면, 두 도메인은 상호 종속적이며, 공통의 관심사 범주에 들어간다고 생각하기 때문.
- 유저가 충전/사용을 하면, 포인트 테이블에 들어 갔는지 안 들어갔는지 또한, 확인이 필요하다.
