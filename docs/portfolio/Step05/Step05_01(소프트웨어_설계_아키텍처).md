#  STEP 05 (소프트웨어 아키텍처 설계)

> 비즈니스 로직 구현을 위해 계층을 분리하고, 소프트웨어의 개발 규모와 유지보수성을 고려하여, 코드의 관심사와 책임을 구성하려면??

## 시스템 또는 프로젝트에서 계층 분리가 필요한 이유??

### 1. 영원한 Software는 존재하지 않는다!
- 사용자의 요구사항을 반영한다는 것?
    - 기존 SW에 불편하거나 없는 것을 추가하고 싶다는 것.
- 내가 짠 코드 또한 시간이 지나거나, 신규/기존 사용자에게 맞지 않는 부분이 발생할 수 있다는 것.

### 2. 변경에 대비한다.
- 현재 사용되고 있는 시스템/서비스 코드에, 새로운 정책이나 수정해야하는 코드가 발생한다면?
  - 특정 정책이 캡슐/모듈화 되어 있지 않고, 수정해야될 로직이 여러 곳에 분포되어 있어, 모든 코드들이 올바르게 수정되었는지 검증/테스트 하기도 어려워짐.
  - 반대로, 작성했던 테스트가 깨질 수도 있다! -> 이는 `기존 기능에 대해 정상적인 실행을 보장하지 않게 됨`.

### 3. 확장에 대비한다.
- 현재 내가 쓰고 있는 코드에 외부 라이브러리가 사용되거나, 기존에 쓰던 특정 모듈이 아닌 대체 모듈이 발생한다면?
  - 이러한 모듈 호출이 하드 코딩이 되었을 경우, 해당 기능 호출부를 수동으로 모두 변경하고 일일이 설정 해줘야한다.
  - 추상화를 통해, 해당 기능을 공통 관심사로 분리한다.
    - 상속을 통해 상위 코드에서 특정 기능을 관리하고, 하위 코드는 해당 고유 기능에 대한 수정/변경에 응집도를 가지며, 필요 시 새로운 모듈을 즉각적으로 적용할 수 있는 구조를 지향

### 4. 함께 일 할 수 있어야 한다.
-  추후 인수인계 시에도 코드 분석에 대한 시간이 오래 걸리기 수 있기 때문에, <br/>
- 특정 기능에 대해 각 클래스와 코드의 책임과 역할을 응집도 있게 작성해둔다면, <br/>
- 처음 보는 코드를 여러 군데에서 헷갈리게 관리할 필요 없이 한 눈에 확인하여 훨씬 더 개발 생산성을 높일 수 있을 것.

## Service Application 에서 가져갈 수 있는 아키텍처 3가지

1. Layered Architecture (계층 분리형)
2. Hexagonal Architecture (도메인 기반의 `포트-어댑터` 관리형)
3. Clean Architecture (`유즈케이스 기반`의 비즈니스 로직 충실형)

--- 
### 1. Layered Architecture (레이어드 아키텍처- 계층 분리형)

- 구조
> [Infra] Presentation -> Business -> Persistence -> Database <br/>
> [Code]  Controller -> Service -> Dao -> Database

각 기능들에 대해서, 단계별 코드 구현을 통해 공통으로 사용되거나 어떤 상황에 호출 되는 기능들을 데이터 처리 관점에서 분리하는 형태

- 각 계층은 정해진 의존성 방향을 지키며 기능 참조를 해야한다! 
  - 해당 계층 구조를 지키지 않고, 하위 -> 상위 호출과 같은 구조가 발생할 경우 문제 발생
    - 각 클래스 간의 관심사 침범(각 계층의 책임을 침범해 결합도가 증가함)
    - 의존성 순환 등으로 인한 테스트 어려움
    - 확장성과 유지보수가 무너지는 코드 짜임새
  - 나쁜 예
    - Repository가 비즈니스 규칙을 처리하려고 Service 호출 
    - Service가 HTTP/세션/Request 같은 Controller 관심사를 들고 있음
    - Entity/DAO에서 외부 API 호출 같은 상위 유스케이스 로직 수행

- 각 계층별 관심사
  - **Presentation**: HTTP, 사용자 입력 검증, 응답 포맷팅
  - **Business**: 비즈니스 규칙, 계산, 워크플로우
  - **Persistence**: SQL, 트랜잭션, 데이터 매핑
  - **Database**: 실제 데이터 저장, 인덱싱, 제약조건

> 레이어드 아키텍처는 도메인 모델이 상대적으로 빈약해질 수 있으나, <br/>
> 명확한 계층 분리를 통해 코드 흐름을 직관적으로 파악하고 관리하기 용이하다는 장점이 있다.

### 2. Hexagonal Architecture(도메인 기반의 포트-어댑터 관리형)

헥사고날 아키텍처는 도메인/유스케이스(inside) 를 중심에 두고,
DB/외부 API/메시징/웹 같은 외부 요소(outside) 를 어댑터로 분리하여 결합을 최소화하는 구조

- 내부는 외부 구현(기술/라이브러리/인프라)에 직접 의존하지 않고, 포트(인터페이스) 를 통해서만 외부와 통신한다.
  - → 결과적으로 외부 구현체가 바뀌어도 포트-어댑터 교체로 대응 가능하며 확장/유지보수에 유리하다.

- 포트 구성
> - Inbound Port: 외부 요청(HTTP, 메시지 등)이 호출하는 유스케이스 인터페이스
> - Outbound Port: 유스케이스가 DB/외부 API 등을 사용하기 위한 의존 인터페이스

- 기능 추상화로 얻는 이점
  - 포트 기반으로 의존성을 역전시켜, 클래스 결합도를 낮추고 책임을 명확히 분리할 수 있다.
  - 테스트 시 외부 인프라 없이 도메인/유스케이스를 단위로 검증할 수 있고, 어댑터를 대역으로 교체하여 명세 기반 테스트(블랙박스 테스트) 를 안정적으로 작성할 수 있다.

`의존성은 항상 외부 -> 내부(Domain)으로 향한다.`

> - Domain은 POJO로 유지하고 프레임워크에 의존하지 않는다.
> - Application(UseCase)은 Port를 통해서만 외부와 통신한다.
> - Web DTO는 Inbound Adapter에서 Command/Result로 변환한다.
> - JPA Entity/외부 API DTO는 Outbound Adapter에서 Domain으로 변환한다.
> - Mapper는 Adapter 영역에 두고, Domain/Application은 Entity/DTO를 알지 못한다.

- Hexagonal Architecture 프로젝트 구조 예시

```js
src/main/java/com/example/commerce
  ├─ common
  │   ├─ config
  │   ├─ exception
  │   └─ util
  │
  ├─ domain
  │   └─ order
  │       ├─ model
  │       │   ├─ Order.java
  │       │   ├─ OrderLine.java
  │       │   └─ Money.java
  │       ├─ policy
  │       │   └─ OrderDiscountPolicy.java
  │       ├─ service
  │       │   └─ OrderDomainService.java        (도메인 규칙이 복잡할 때만)
  │       └─ port
  │           └─ out
  │               ├─ LoadOrderPort.java
  │               └─ SaveOrderPort.java
  │
  ├─ application
  │   └─ order
  │       ├─ port
  │       │   └─ in
  │       │       ├─ PlaceOrderUseCase.java
  │       │       └─ CancelOrderUseCase.java
  │       ├─ service
  │       │   ├─ PlaceOrderService.java         (유스케이스 구현)
  │       │   └─ CancelOrderService.java
  │       └─ dto
  │           ├─ command
  │           │   └─ PlaceOrderCommand.java     (inbound용)
  │           └─ result
  │               └─ OrderResult.java           (inbound 반환용)
  │
  ├─ adapter
  │   ├─ in
  │   │   └─ web
  │   │       ├─ OrderController.java
  │   │       └─ dto
  │   │           ├─ request
  │   │           │   └─ PlaceOrderRequest.java (HTTP 전용 DTO)
  │   │           └─ response
  │   │               └─ OrderResponse.java
  │   │
  │   └─ out
  │       ├─ persistence
  │       │   ├─ jpa
  │       │   │   ├─ OrderJpaEntity.java
  │       │   │   ├─ SpringDataOrderRepository.java
  │       │   │   └─ OrderPersistenceAdapter.java  (Port 구현체)
  │       │   └─ mapper
  │       │       └─ OrderEntityMapper.java        (Domain ↔ Entity)
  │       │
  │       └─ external
  │           ├─ PaymentClientAdapter.java
  │           └─ dto
  │               └─ PaymentApiRequest.java
  │
  └─ BootstrapApplication.java
```

1) OrderController(in adapter) <br/>
→ 2) PlaceOrderUseCase(application, 포트로 접근)<br/> 
→ 2-1) PlaceOrderService (어댑터 접근, DIP/추상화) <br/>
→ 3) LoadOrderPort / SaveOrderPort(out port, 인터페이스)<br/>
  → 3-1) OrderPersistenceAdapter(out adapter, 구현체)<br/>
→ 4) SpringDataOrderJpaRepository(Spring Data JPA)<br/>
→ 5) DB<br/>

```js
[In Adapter]
OrderController
        │
        ▼
[Inbound Port]
PlaceOrderUseCase
        ▲
        │
[UseCase Impl]
PlaceOrderService
        │
        ▼
[Outbound Port]
LoadOrderPort / SaveOrderPort
        ▲
        │
[Out Adapter]
OrderPersistenceAdapter
        │
        ▼
SpringDataOrderJpaRepository
        │
        ▼
DB

```

### 3. Clean Architecture (정책 중심의 의존성 관리 구조)

클린 아키텍처는 시스템에서 가장 중요한 비즈니스 정책을 중심에 두고,
덜 중요한 구현 세부사항(웹, DB, 프레임워크 등)을 바깥으로 분리하는 구조이다.</br> 
`(헥사고날과 다르게 입/출력이 기준이 아님.)`

모든 의존성은 항상 안쪽(핵심 정책) 을 향하며,
도메인과 유스케이스는 외부 기술 및 프레임워크의 변경으로부터 보호된다.

핵심 비즈니스 규칙은 외부 환경에 의해 영향을 받지 않아야 하며,
UI, DB, 프레임워크는 언제든 교체 가능한 세부 구현으로 취급한다.

```
[계층 구조 (의존성 방향)]

Entities
↑
Use Cases
↑
Interface Adapters
↑
Frameworks & Drivers
```

- Entities : 시스템 전반에서 가장 중요한 엔터프라이즈 비즈니스 규칙(도메인 모델)
- Use Cases : 애플리케이션의 유스케이스 흐름과 정책을 정의
- Interface Adapters : 외부 입력/출력을 유스케이스가 이해할 수 있는 형태로 변환
- Frameworks & Driver : Web, DB, 메시징, 외부 API 등 구체 기술 구현 영역


`DB/FraemWork/UI는 바뀔 수 있지만, 가장 중요한 비즈니스 정책은 쉽게 변할 수 없다.`

> 헥사고날에서는 도메인과 유스케이스가 자연스럽게 섞여 보이기도 하지만, 클린은 이 둘을 엄격히 구분한다.

** Entities
- 엔터프라이즈 수준 규칙
- 여러 애플리케이션에서 재사용 가능
- 불변조건, 핵심 비즈니스 로직

** Use Cases
- “이 애플리케이션에서의” 흐름
- 트랜잭션 경계
- 입력/출력 모델 정의

=> 클린은 도메인 로직을 유스케이스와 섞지 않으려는 경향이 강함
