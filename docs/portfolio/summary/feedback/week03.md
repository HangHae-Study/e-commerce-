- 모든 클래스의 책임을 검증하기 위한 각각의 클래스의 단위테스트 구성이 전혀 되어있지 않네요. 모든 레이어의 컴포넌트들이 각 책임을 부여했다면 그 책임이 잘 수행되는지 검증을 위한 단위테스트가 필요합니다. 그게 우리 1주부터 배웠던 TDD이구요.

- OrderFacade는 다양한 도메인을 통해 전체 비즈니스를 관리하는 역할을 잘 수행한 것 같은데, ProductDetailFacade는 Product와 ProductLine이 동일한 도메인이라면 파사드가 필요했을까 싶기는 합니다.

- 일단 도메인과 ORM을 분리하는 것은 잘 하신 것 같은데, N+1 등의 이슈는 또 해결해야하는 문제겠지요. N+1은 도메인과 JPA를 분리하지 않아도 잘 발생하는 이슈긴 해요.

- Order 도메인의 생성은 파사드가 아닌 OrderService에 위치했으면 어땠을까 싶네요. 여러 도메인 로직을 수행하기 위해 각 도메인 서비스를 호출해서 흐름을 관리한다면 도메인 생성의 역할은 부여되지 않는 것이 좋을 것 같습니다.

- 유저와 포인트 도메인이 나뉘어진건지 합쳐진건지 잘 모르겠네요. 합쳐졌다면 User를 중심으로 클래스를 설계하면 클래스 수를 더 줄일 수 있을 것 같습니다. 필요하지 않은 Facade 레이어도 제외할 수 있을 것 같구요.

- 락이라는 행위를 프록시 패턴으로 구사하는 것이 저는 적절한지 모르겠습니다. 추후에 배우겠지만, 동시성 제어를 하는 방식이 꼭 락만 있는 것은 아니고 카프카등을 활용하면 락을 사용하지 않고도 비즈니스를 처리할 수 있는데 이미 비즈니스가 락에 종속된 형태여서 좋은 구조가 아닌 것 같습니다. 동시성 제어에 대한 자세한 설명은 추후에 진행할게요.
