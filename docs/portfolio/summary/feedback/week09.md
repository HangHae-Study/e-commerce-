 - 카프카 개념 정리한 문서가 좋아요. 또, 실시간 주문 정보 전송이나 쿠폰 설계에 대한 시퀀스 다이어그램이 잘 그려져 있어 이해하기 좋았어요. Outbox 패턴까지 잘 적용했네요.
 - 컨슈머의 layer는 트랜잭션을 관리하는 역할은 갖지 않는게 일반적이에요. 단일책임원칙 기반으로 생각해도, 이 클래스의 역할은 트랜잭션을 처리하기보다 메시지를 잘 가져와서 어플리케이션의 메서드를 잘 호출하여 비즈니스를 수행하고 메시지를 정상적으로 커밋하거나, 예외가 발생했을 때, 재시도를 하거나 DLQ로 전달하는 등의 역할을 하는게 책임이 분리된 설계로 볼 수 있을 것 같아요. 이렇게 컨슈머에 로직을 구현하면 테스트코드를 작성하기도 힘들거에요. 비즈니스와 저수준모듈이 결합되어있는 클래스여서..
 - 선착순 쿠폰에서는 모든 요청에 대해 카프카에 메시지를 적재하기보다 재고가 없는 경우 쿠폰 발급 요청을 빠르게 실패처리하는 구현이 성능 관점에서 유리한 설계로 보여요. 다만, 컨슈머에서 processCouponIssue 이후에 newCouponIssueWithOutDistLock을 수행하다가 실패하는 경우 쿠폰 재고를 다시 올려야하는데 그 부분이 보이지 않고 구현한다고 하더라도 복잡도가 있어보여요.
 - 대부분 자동 커밋을 활용해요. 예전에는 좀 구분해서 썼었는데 오히려 신경쓸 부분이 더 많아지는 것 같아요. 컨슈머에서 트랜잭션이 실패하더라도 ack를 할지 ack를 하지 않고 재시도를 할지를 컨슈머에서 구현을 통해 결정할 수 있을 것 같아요. 이 컨슈머에서 별도의 비동기 흐름이 필요하다면 추가할 수도 있겠지만 비동기의 꼬리를 물고 물리면 복잡도가 올라갈 수도 있을 것 같아요.
 - 테스트케이스가 실패한 것은 컨슈머가 메시지를 처리할 시간을 주지 않고 테스트케이스가 종료되어 컨슈머 스레드가 강제로 끊긴 상황은 아닌가요?
