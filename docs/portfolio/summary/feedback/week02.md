    - 분산 Lock방식의 경우, DB 트랜잭션이 끝나기 까지의 과정을 모두 한번에 가져갈 수 있다는 점이 있다는 것으로 보았고,
    - 원자적 감소 같은 경우, 조회 시 잔여 수량이 음수일 경우 더 이상 잔여 쿠폰이 없는 것으로 확인하는 방향으로 사용할 수 있을 것 같습니다.
    - 원자적 감소의 경우, DB 트랜잭션에서 문제 발생시 또는 내부 로직에 따라 redis의 잔여 수량을 다시 원복하는 과정에서, 유저 입장에서 잔여 쿠폰에 대한 경계가 모호해질 것 같은데,, 때에 따라 다르겠지만 보통은 분산 Lock 방식을 주로 사용하는 것이 올바른가요??

REST 규칙에 따라서 API를 문서화하였는가?: O

- 전체적인 흐름과 시간순으로 표현하기 위한 문서는 시퀀스다이어그램보다는 플로우차트가 더 효과적입니다.

- 현업에서는 결제와 주문은 분리하는 편입니다. 결제는 외부 PG 혹은 은행, 카드사등의 승인 프로세스가 포함되는데 이런 외부 트랜잭션과 내부의 트랜잭션을 별도의 프로세스로 분리하는 것이 시스템 안정성 차원에서도 유리합니다. 도메인의 분리 기준은 명확하게 딱 떨어지는 정답이 없어서 시원하게 설명은 어려운데요, 저는 각각의 비즈니스를 구현하면서 비즈니스 로직의 책임을 분리함으로써 도메인을 생각하는 편입니다.

- 동시성 제어는 추후에 상세히 설명해드릴게요.

- Mock api는 사용처에서 기대하는 동작을 제공하지 않기에 return null 로 200으로 항상 응답해도 괜찮습니다. 다만 문서에 예외에 대해 표현하기 위해 어노테이션을 통해 발생할 수 있는 상황을 미리 정의해두는 것은 괜찮습니다.

- 추후 요구사항에 따라 반드시 요청 응답이 변경하지 않는 상황이 대부분이었고, 상세 스펙에 의해 요구사항이 변경되는 상황에 대해서는 인터페이스가 변경될 수 있으나 최소화될 수 있도록 초기 설계를 구체적으로 하는 것을 권장합니다.
