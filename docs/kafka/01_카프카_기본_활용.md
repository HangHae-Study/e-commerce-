
### 용어 미리 깔고 가기
- `Producer` - 메세지를 카프카 브로커에 적재(발행)하는 서비스
- `Consumer` - 카프카 브로커에 적재된 메시지를 읽어오는(소비) 서비스
  - 메세지를 읽을 때마다 파티션 별로 offset을 유지해 처리했던 메세지의 위치를 추적
  - `CURRENT-OFFSET` 
    - 컨슈머가 어디까지 처리했는지를 나타내는 offset 이며,  동일한 메세지를 재처리하지 않고, 처리하지 않은 메세지를 건너뛰지 않기위해 마지막까지 처리한 offset을 저장(커밋)해야함
    - 만약 오류가 발생하거나 문제가 발생할 경우, 컨슈머 그룹 차원에서 `--reset-offsets`  옵션을 통해 특정시점으로 offset을 되돌릴 수 있음
  

- `토픽 (Topic)`
  - 메세지를 담는 통
- `파티션 (Partition)`
  - 토픽을 여러 조각을 나눈 것(병렬/확장 단위)
  - 각 파티션은 리더(Leader)와 1개의 팔로워(Follower) 복제본들로 구성
- `ISR(In-Sync Replicas)`
  - 리더와 동일 오프셋 까지 따라붙은 "정상 복제본" 집합. 장애 시 새 리더를 뽑을 후보군


- `브로커 (Broker)` : 카프카 서버 프로세스 (메세지 저장/전달)
- `컨트롤러 (Controller)`
  - 다른 브로커를 모니터링하고 장애가 발생한 Broker에 특정 토픽의 Leader 파티션이 존재한다면, 다른 브로커의 파티션 중 Leader를 재 분배하는 역할 수행
  - 컨트롤러는 각 파티션과 복제본에 대해 상태 전이를 관리한다(예: NewPartition → OnlinePartition, 리더 교체, 복제본 Online/Offline/삭제 등)
- `Coordinator`
  - 컨슈머 그룹을 모니터링하고 해당 그룹 내의 특정 컨슈머가 장애가 발생해 매칭된 파티션의 메세지를 Consume 할 수 없는 경우, 해당 파티션을 다른 컨슈머에게 매칭해주는 역할 수행 (`Rebalance`)

### Zookeeper - Kafka 통신 방식
https://cwiki.apache.org/confluence/display/KAFKA/Kafka%2Bdata%2Bstructures%2Bin%2BZookeeper
1. 브로커 기동 → “살아있다” 등록 
   - 브로커는 ZK에 `/brokers/ids/{brokerId} `를 ephemeral 노드로 등록한다(세션이 끊기면 자동 삭제 → 장애 감지). 
   - 다른 구성원(컨트롤러 등)은 `/brokers/ids` 경로를 watcher로 감시하고, 변화가 생기면(추가/삭제) 반응한다.
     - `/brokers/ids` : 살아있는 브로커 목록
   > - 컨트롤러는 "브로커 중 1대가 맡는 역할", 개별 서버(브로커) 중 한 대가 컨트롤러로 선출되어 클러스터 상태 전이를 지휘
   > - /brokers/ids의

   - 추가(새 브로커 등장)
     - 컨트롤러가 /brokers/ids 변경을 감지 → 활성 브로커 집합을 갱신하고, 필요 시 메타데이터를 UpdateMetadata RPC로 전체에 전파
     - (즉시 리더가 바뀌는 건 아니고, 재배치 계획이 있으면 그때 반영).
   - 삭제(브로커 다운)
     - 해당 브로커의 ephemeral 노드가 사라짐 → 컨트롤러가 브로커 장애로 간주하고, 그 브로커가 리더였던 파티션에 대해 ISR에서 새 리더를 선출해 
     - .../state 를 갱신한 뒤 LeaderAndIsr / UpdateMetadata 같은 RPC로 각 브로커에 반영


2. 컨트롤러 선출 
   - 모든 브로커가 시작 시 /controller 라는 ephemeral znode 만들기를 시도한다. 먼저 성공한 브로커가 컨트롤러가 된다(이미 있으면 “exists” 오류 받고 패스). 
   - 컨트롤러 세션이 끊기면 /controller가 사라져 즉시 재선출이 트리거된다(다른 브로커가 다시 create 시도).


3. 토픽 생성/변경 반영 
   - 토픽·파티션 배치 정보는 /brokers/topics/{topic} 및 /brokers/topics/{topic}/partitions/{p}/state 등에 기록된다. 
   - 컨트롤러는 해당 변경(새 파티션 등장, 리더/ISR 갱신 등)을 감시하고 리더 선출/ISR 조정 후, 모든 브로커에 LeaderAndIsr / UpdateMetadata 요청을 보낸다(직접 RPC).
   

4.  브로커 장애 처리
   - 어떤 브로커가 죽으면 그 브로커의 ZK 세션이 만료 → /brokers/ids/{id} 가 자동 삭제된다(ephemeral 특성). 
   - 이를 watcher로 감시하던 컨트롤러가 즉시 감지하고, 해당 브로커가 리더이던 파티션들에 대해 새 리더를 ISR에서 선출하여 ZK의 state 를 갱신하고, 관련 브로커들에게 LeaderAndIsr/UpdateMetadata 를 보낸다.


5. ISR 변화 전파 
   - ISR이 줄거나 늘면 브로커가 /isr_change_notification/ 아래에 노드를 만들고, 컨트롤러는 그것을 watch 하다가 메타데이터 업데이트를 전체에 전파한다.
   
### `Producter/Consumer` 주키퍼 바라보는 법
1. 프로듀서는 메타데이터 요청으로 “특정 파티션의 현재 리더가 누구인지”를 아무 브로커에게나 물어본다
2. (브로커들이 컨트롤러로부터 받은 최신 메타데이터를 갖고 있음). 
3. 그래서 중간 라우팅 계층 없이 리더에게 직행한다. 
4. 리더가 바뀌면 메타데이터 갱신 후 새 리더로 자동 전환.

### ZooKeeper vs KRaft
- ZooKeeper: 분산 시스템에서 "합의(leader 선출), 메타 데이터 저장, 워치" 를 담당하는 별도 코디네이터
  - Kafka 2.8 이전 버전에서 브로커 메타데이터/토픽정보/리더선출 을 ZooKeeper에 의존
- KRaft(Kafka Raft): Kafka가 자체적으로 Raft 합의 알고리즘을 구현해 컨트롤러가 ZooKeeper 없이 메타데이터를 관리하는 모드.
  - 별도의 ZooKeeper를 안가짐.

### Kafka에서 주키퍼란?
- 외부 시스템 (ZooKeeper)에 메타 데이터 저장 
  - 브로커는 주키퍼와 통신, 컨트롤러 선출/토픽 상태 관리도 주키퍼 경유하게됨.
  - 운영 포인트 증가

### Kafka Raft란?
- 카프카 내부에 컨트롤러 쿼럼(Raft)이 메타데이터 로그 관리 
  - 브로커는 컨트롤러와 리더와 대화. 주키퍼 필요 X, 배포/운영 단순화


### 파티션과 복재본
KRaft의 장점 : `파티션 리더 선출`
- 파티션(Partition): 한 토픽을 여러 “조각”으로 쪼개 병렬 처리·확장을 가능하게 하는 수평 분할 단위 
  - → 많을수록 처리량/컨슈머 병렬성↑, 토픽 내 순서 보장은 “각 파티션 안에서만” 유지.

- 복제본(Replica): 각 파티션을 여러 브로커에 복사해 두는 내구성·가용성 단위
  - → 많을수록 장애 내성↑(디스크/브로커 고장 시 생존), 저장 공간/네트워크 비용도 같이↑.

> 파티션 = 속도·병렬성, 복제본 = 안전성·가용성. 
> 한 토픽은 “여러 파티션”을 가질 수 있고, 각 파티션마다 여러 복제본이 존재

| 항목         | 파티션                          | 복제본                     |
| ---------- | ---------------------------- | ----------------------- |
| 목적         | 처리량·병렬성                      | 내구성·가용성                 |
| 적용 대상      | **토픽**을 쪼갬                   | **파티션**을 복사             |
| 순서 보장      | 파티션 **내에서만**                 | 영향 없음(리더가 순서 결정)        |
| 컨슈머 병렬성    | **파티션 수**만큼 병렬 소비 (컨슈머그룹 기준) | 변화 없음                   |
| 저장/네트워크 비용 | 파티션 수만큼 인덱스/세그먼트 증가          | **복제계수**만큼 데이터 총량 증가    |
| 장애 대응      | 직접적 영향 없음                    | 리더 장애 시 **팔로워 승격**으로 지속 |

```
예: 토픽 orders

파티션 수 = 3 (P0, P1, P2)

복제계수(RF) = 3 (각 파티션을 3개 브로커에 복제)

Broker1      Broker2      Broker3
P0[L]        P0[F]        P0[F]
P1[F]        P1[L]        P1[F]
P2[F]        P2[F]        P2[L]

각 파티션은 리더 1개 + 팔로워들로 구성.

프로듀서는 리더에게만 쓰고, 컨슈머도 보통 리더에서 읽음.

리더가 죽으면 컨트롤러가 동기화된 복제본(ISR) 중 하나를 새 리더로 선출.
```
